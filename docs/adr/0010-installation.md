# Installation writes the host registry; symlink the extension and copy the Collector

OpenChamber does not scan extension directories to discover extensions. Putting a directory under `~/.config/openchamber/extensions/` does not make it appear in the rail; it must be registered in `paths` in `~/.config/openchamber/extensions.json`. Without `service` in `capabilityGrants["context-map"]`, the panel opens but every host request returns `NOT_GRANTED`. Installation therefore has to modify the host's configuration file; `bun run install` is not a plain copy script.

The extension is a symlink to the repository root, so the repository remains the single source and a restart of OpenChamber after `git pull` picks up changes. The Collector is a single file copied to `~/.config/opencode/plugins/context-map.js` with a `// @context-map-collector v<version>` marker at the top: OpenCode loads files from the plugin directory, a copy is closer to how it actually runs than a symlink, and the marker lets install and uninstall distinguish files generated by this tool from the user's own plugins.

A second path installs the extension from a Git URL in OpenChamber. The host copies the package and registers it, and no repository script runs. That path cannot create the Collector, so the Service writes it on request from the panel; see [0015](0015-panel-collector-install.md). Both paths use the same marker and conflict rules.

When writing `extensions.json`, the installer first parses the file and validates the shape of known fields, then writes the whole file back with unknown fields preserved. Writes use a temporary file plus `rename`, with mode 0600. `storageIds` is not generated; the host fills it in the first time it lists extensions. The installer accepts only an empty extension target, a symlink pointing at this repository, or a Collector file carrying the marker; the panel endpoint accepts only a missing Collector file or one carrying the marker. Anything else leaves the original file untouched; the installer exits non-zero and the panel endpoint returns 409.

**Considered options**

- Copy the extension directory instead of symlinking: upgrades require reinstalling, and two copies drift apart.
- Generate `storageIds` automatically: the format is the host's decision, and a wrong guess pollutes the storage mapping.
- Overwrite existing targets: would delete the user's own plugins or extension directories as if they belonged to this tool.
- Symlink the Collector too: easier upgrades, but file ownership and version detection would depend on the link target, and it diverges from how OpenCode loads plugins.

**Consequences**

The repository must stay at a stable path; moving or deleting it breaks the extension symlink. A link install has no such requirement. Install and uninstall rewrite `extensions.json`, and a running OpenChamber may write the same file at the same time, so the README requires fully quitting the host first. If a host upgrade changes the registry structure, the validation in `parseExtensionStore` makes installation fail instead of writing a file the host cannot read. The panel path needs the `service` grant and writes only the default OpenCode plugin path.
